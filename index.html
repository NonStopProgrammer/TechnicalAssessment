The pipeline

A pipeline is a definition, not a program.

In Phoenix, a pipeline is one YAML spec plus SQL files, versioned in Git. The engine — Apache Spark, on YARN on-prem and Dataproc on GCP — does the engineering once. Every feed inherits it.

01

Ingest — from anywhere, incrementally

Pluggable readers pull from Oracle, SQL Server, any JDBC source, files on SFTP/NFS/HDFS/GCS, or Kafka streams. Watermark bookkeeping means each run reads only what's new since the last success — and schema is captured on read, so drift is caught at the door.

02

Curate — business logic is SQL

Transformations are a chain of Spark SQL steps — standardize → enrich → curate — each one a named view for the next, parameterized by run date and environment. Analysts write it; Git reviews it; nobody writes engine code.

03

Validate — nothing unproven lands

A data-quality gate sits between transform and write: null, uniqueness, row-count, referential and custom SQL rules, each with an explicit outcome — fail the run, warn, or quarantine the offending records below a threshold. Source-vs-target reconciliation runs on every load.

04

Deliver — idempotent, everywhere

Writers land data in Cloudera Hive, GCP BigQuery, any JDBC target, or partner file extracts with headers, trailers and control totals. Every write is idempotent — partition overwrite or keyed merge — so any rerun, any backfill, is boring.

Architecture

One platform, five planes.

Definitions live in Git. A control plane schedules and validates. Spark executes. The Healing Agent watches every run. Observability receives everything. The moving dashes show live data and event flow.

Reading the diagram: blue moving dashes are the data path through a run; green dashes are the event loop between execution and the Healing Agent — failure events flow out, bounded remediation actions flow back. The agent plane is deliberately separate from execution: healing logic is written once, for every pipeline.

The agent plane

Meet the Healing Agent.

Not a dashboard. Not a cron job that pokes the Spark UI. A small, always-on control service that treats every failure as an event to be handled — with bounded, audited actions.

LAYER 1 · IN-FLIGHT GUARDS

Inside the Spark job

The framework itself handles what's cheap to handle in place: fast retries with backoff on transient errors, bad-record routing to quarantine mid-flight, checkpoint and watermark commits so state is never ambiguous.

If the job still dies, it dies loudly — emitting a structured failure event with the exception chain, stage, metrics and run context.

LAYER 2 · THE HEALING AGENT

Outside the job, always on

A lightweight long-running service — on-prem as a supervised daemon, on GCP as a Cloud Run service. It is event-driven, not polling: it subscribes to run lifecycle and failure events written by every job.

On a terminal failure it classifies → decides → acts: resubmits through AutoSys or Composer APIs with retuned resources, evolves a compatible schema, opens a circuit breaker, or escalates with full context. Then it verifies — DQ re-check, counts reconciled — before calling anything healed.

So is it long-running, and does it monitor Spark?

Long-running: yes. Watching Spark's UI: no. Every Phoenix run writes lifecycle events (started, stage completed, failed, succeeded) to the metadata store as it executes. The agent consumes those events the moment they land — reaction time is seconds, and the logic is restart-safe because all of its state lives in the database, not in memory. As a safety net, a reconciliation sweep runs every few minutes to catch the one case events can't cover: a driver killed so abruptly it never wrote its own failure event. Heartbeat missing → treated as a failure event → same healing path. Every action the agent takes is recorded in the healing audit and is idempotent — two agents, or an agent restarting mid-action, can never double-fire a remediation.

AI FOR THE LONG TAIL

Diagnosis, with guardrails

For failures no rule can name, an AI model reads the logs, run history and healing audit, and returns a diagnosis plus a proposed action. It may only execute actions already on the pre-approved runbook list — anything novel goes to a human, diagnosis attached. Every AI decision is audited like any other.

Trust, built in

Everything watches. Everything is written down.

Every run emits one correlated envelope — run-id, pipeline, versions, stage — so logs, metrics, quality and audit all join.

LOGGING

Apache Log4j2

Structured JSON, one schema, run-id on every line, driver and executor logs unified — no grep archaeology.

OBSERVABILITY

Splunk

Logs and metrics flow to Splunk over HEC: health dashboards, alerts on failure class and SLA risk, saved searches per failure taxonomy.

AUDIT

Audit tables

Runs, versions, row counts, DQ results, healing actions, schema changes — 13 months, query-ready. Regulator questions become SQL.

NOTIFICATIONS

Tiered email & escalation

Self-healed → daily digest. Degraded → team email. Escalated → ticket + page with full context. Tier one never wakes anyone.

SLA

Predictive SLA watch

Stage-duration history predicts misses and alerts before the deadline — not after the report is late.

GOVERNANCE

Lineage & policy

Lineage events per run into the enterprise catalog; PII tags in the spec enforce masking before any write; per-pipeline service accounts.

Deployment

One artifact. Two worlds. Zero drift.

Everything ships from Git through Harness — framework releases and pipeline configs alike. On-prem and GCP are stages of the same release, so versions can never silently diverge. Rollback is repointing to the previous immutable artifact.

  • Spark on YARN — the approved cluster
